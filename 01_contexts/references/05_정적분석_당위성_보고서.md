## 핵심 논지 요약

본 보고서는 HLF 체인코드 보안에서 **동적 분석(Fuzzing)보다 정적 분석(Static Analysis)이 우월하다**는 주장을 3가지 축으로 정당화한다.

## 1. "Consensus vs. Crash" 논거

### 핵심 주장
- Fuzzing은 **런타임 크래시(Crash)** 탐지에 최적화
- HLF의 가장 치명적 버그는 **합의 불일치(Consensus Failure)** — 크래시가 아닌 "정상 실행"으로 나타남
- 단일 노드 Fuzzing에서는 비결정론적 코드가 성공적으로 실행되어 "안전"으로 오판

### 근거 논문
- Yang et al. (2021): Fluffy — 합의 버그 탐지는 Differential Fuzzing(다중 노드 비교) 없이 불가능에 가까움
- Differential Fuzzing의 HLF 적용 비용: Docker 컨테이너 + gRPC → 초당 수천 입력이 아닌 "입력당 수초" → 통계적으로 무의미

### 정적 분석의 우위
- GoLiSA 등의 도구: 비결정론적 소스(`time.Now()`, `range map`)에서 민감한 싱크(`PutState`)로의 정보 흐름을 구조적으로 추적
- 실행 없이 밀리초 단위로 합의 위험 식별 가능

## 2. "Harness Complexity Barrier" 논거

### EVM vs HLF 구조적 차이
| 항목 | Ethereum (Solidity) | Hyperledger Fabric (Go) |
|:-----|:-------------------|:-----------------------|
| 환경 | 폐쇄적, 결정적 EVM | 표준 바이너리 + gRPC + 외부 DB |
| 상태 | Merkle Patricia Trie | CouchDB/LevelDB 추상 레이어 |
| Harness | `test_fuzz(uint)` 한 줄 | 전체 Docker 네트워크 + gRPC 프로토콜 모킹 |
| Mock 도구 | EVM이 곧 환경 | MockStub (기능 제한적) |

### MockStub의 한계 (실측 근거)
- **Rich Query 미지원**: CouchDB JSON 쿼리(`GetQueryResult`) 호출 시 즉시 에러/패닉 → 관련 코드 경로 도달 불가
- **MVCC 미시뮬레이션**: 단일 스레드 순차 실행 → 읽기-쓰기 충돌, 팬텀 리드, 버전 의존성 탐지 불가
- **Integration Harness 비용**: 실제 Peer/Orderer/CouchDB Docker 네트워크 → 트랜잭션당 수초 지연 → Fuzzing 요건(초당 수천 실행)과 배치

### 근거 문서
- Oracle (2024): Hyperledger Fabric MockStub Limitations
- Olivieri et al. (2024): Phantom Read Detection Limitations in MockStub

## 3. "LLM as Semantic Static Analyzer" 논거

### Semantic Gap 문제
- 전통 정적 분석(GoLiSA): 구조적 결함(비결정론, 오염 흐름) 탐지 우수
- 전통 정적 분석 한계: **"비즈니스 로직"** 취약점 탐지 불가 — 변수가 "오염"되었는지는 알지만, 비즈니스 요구사항상 오염되어야 하는지는 모름

### sLM의 역할
- 함수명(`updateAssetOwner`)과 문맥에서 소유권 검사가 의미론적으로 필요하다고 **추론** 가능
- Linter(문법) → Static Analyzer(흐름) → **sLM(의미)** 3단계 심화

### 근거 논문
- SADA (2024): LLM 에이전트가 정적 도구가 놓치는 코드 패턴("Risky Mutable Proxy") 탐지 입증
- Forge (2026, ICSE): LLM이 감사 보고서에서 취약점 데이터셋을 자동 추출, 계층적 분류 수행
- Reentrancy Detection (2025, arXiv 2505.19059): 1-3B 파라미터 sLM을 Fine-tuning하여 대형 모델에 비견되는 탐지율 달성

### 로컬 sLM의 기업 환경 적합성
- **데이터 주권**: HLF는 프라이버시 목적으로 선택 → 독점 체인코드를 클라우드 모델(GPT-4)에 전송은 모순
- **자원 효율성**: Phi-3, 양자화 Llama-3 등 소비자 하드웨어에서 구동 가능
- **적대적 복원력**: 도메인 특화 Fine-tuning된 로컬 모델이 범용 LLM보다 난독화 공격에 강건

## 4. 비교 분석표 (보고서 원문 Table 1)

| 취약점 유형 | Dynamic Fuzzing | Formal Static Analysis | Semantic SA (sLM) | SA/sLM 우위 근거 |
|:-----------|:---------------|:----------------------|:-----------------|:----------------|
| 비결정론 (합의) | Ineffective | High | Medium | Fuzzing은 단일 노드 state divergence 놓침 |
| 팬텀 리드 (MVCC) | Very Low | High | High | Fuzzing은 정밀한 트랜잭션 타이밍 필요 |
| Rich Query 로직 | Impossible (MockStub) | Medium | High | MockStub이 rich query에서 크래시 |
| 접근 제어 (비즈니스 로직) | Low | Low | High | Fuzzer는 입력만 변이; sLM은 의도 추론 |
| 설정 비용 | Prohibitive | Minimal | Minimal | Fuzzing HLF는 복잡한 Docker 오케스트레이션 필요 |
| 프라이버시 보존 | Medium | High | High | 클라우드 분석은 기업 프라이버시 위반 |

## 5. 제안 방법론: 하이브리드 엔진

- **Stage 1: Formal Static Analysis ("Hard" Filter)**: SSA 기반 분석기 → CFG/DFG 구축 → 비결정론/오염 흐름 결정적 식별
- **Stage 2: Semantic Analysis ("Soft" Filter)**: 고위험 코드 세그먼트를 로컬 sLM에 전달 → 접근 제어 검사, rich query 의도 파싱, Stage 1 오탐 필터링
- **Reporting**: 형식적 방법의 수학적 확실성 + AI의 의미론적 통찰 결합

## 6. 핵심 논거 4줄 요약 (논문 방어용)

1. **Argument 1 (Consensus Blind Spot):** Fuzzing은 크래시 탐지용. HLF 취약점은 단일 노드에서 정상 실행되나 네트워크에서 합의 실패. Differential Harness 없이 탐지 불가.
2. **Argument 2 (Harness Barrier):** MockStub은 CouchDB Rich Query, MVCC 미지원. 실제 환경 Harness 구축은 Fuzzing 처리량 이점 상실.
3. **Argument 3 (Static Precedent):** GoLiSA 등이 팬텀 리드/비결정론 탐지에서 정적 분석의 우월성 입증. 구조적 문제이지 순수 런타임 의존이 아님.
4. **Argument 4 (Semantic Bridge):** 로컬 sLM이 비즈니스 로직 결함 탐지 + 오탐 감소. 실행 비용/프라이버시 위험 없이 동적 관찰의 "지능" 제공.
